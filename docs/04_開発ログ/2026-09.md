# 開発ログ 2026-09

## 2026-09-08 ご案内モーダルの文言見直し（ISS-053）

### 概要

「ご案内」モーダル内の文言を4箇所修正し、1箇所を削除した。あわせて、新しい
チャットセッションで開発フロー（ISS起票→実装→Commit・Push）を踏み直した。

### 実施内容

**文言修正**

- 使い方セクションの見出しを「ココロの乗り換え案内（使い方マニュアル）」から
  「使い方のご案内」へ変更
- 切符表・コーピング行の「こんなとき」を「緊張、怒り、おっくうな時」から
  「さまざまなストレスやプレッシャー、つらさがあるとき」へ変更
- AI機能の説明を、個別の機能名（お守りAI相談・コラム要約）に依存しない表現へ変更
- 「無料での取得・登録が1ステップで行えます」から「1ステップ」の表現を削除
- ご意見・不具合目安箱の説明文を段落ごと削除（フォーム・メールのボタンは維持）

**フローの踏み直し**

- 修正の実装が先行してしまったため、事後に[[ISS-053]]を起票し、
  [[ISS一覧]]・[[リリース履歴]]・次の停車駅Excelを更新
- Commit `fix(ISS-053): ご案内モーダルの文言見直し`、
  `docs: ISS-053公開に伴うISS一覧・リリース履歴の更新` の2件をPush

**バックログの不整合を発見**

- Excelへの起票作業中に、Excelと `01_PBL/ISS一覧.md`・`02_ISS/` の記載が
  食い違っていることに気付き、[[ISS-054]]として起票

### 目的

ご案内モーダルの文言を、利用者にとって分かりやすく、かつ機能追加時に実態と
ずれにくい表現に整える。

### 所感

新しいチャットセッションを開いたことで、AI側が既存の開発フロー（ISSを起票してから
実装する）を踏まずに、いきなりindex.htmlを直してしまった。フロー自体は
`AGENTS.md` と `docs/` に残っており失われていなかったので、事後にISSを起票して
辻褄を合わせた。セッションが変わった直後は、AI側にフローを踏ませる指示を
明示的に出すか、こちらから確認する運びにしたい。

## 2026-09-08〜09 ご案内モーダルの修正が公開されなかった件（ISS-055）

### 概要

ISS-053の修正をCommit・Push済みにもかかわらず、公開サイトに反映されない事象が
発生した。原因は `netlify.toml` に起因する独立した2件で、いずれも設定の修正で
解消した。詳細な原因分析は[[ISS-055]]を参照。

### 実施内容

**発覚（9-09 朝）**

- スマホの実機でご案内モーダルを開いたところ、旧文言のままだった
- 当初はホーム画面アイコン経由のキャッシュを疑ったが、公開サイトのHTMLを
  直接取得して確認したところ、配信されているHTML自体が旧版だった。
  キャッシュではなく、実際に未デプロイだったことが確定

**原因1の特定：ビルドスキップ判定が浅い**

- Netlifyのデプロイログから、ignoreコマンドが `git diff --quiet HEAD^ HEAD -- . ':!docs'`
  であることを確認。直前の1コミットしか見ていない
- 9-08のPushは2回に分かれており、2回目（docsのみ）が1回目（index.html）の
  ビルドをキャンセルしたうえで「docs以外に変更なし」と判定されていた
- 結果、index.htmlの変更がどのデプロイにも含まれないまま取り残されていた

**原因2の特定：公開範囲がリポジトリ全体**

- 手動デプロイを試したところ、今度は
  `Invalid filename 'docs/ekicho-dayori/#3_v1.pptx'` でビルドが失敗
- `publish` の指定がなく、リポジトリルートがそのまま配信対象になっていたため、
  `docs/` 配下も公開対象に含まれていた（`AGENTS.md` が公開URLで取得できることを確認）

**修正（9-09 午前）**

- PCが手元になかったため、GitHubのWeb UIから `netlify.toml` を直接編集
- `command` / `publish` を追加して配信対象を `index.html` と `assets/` のみに限定し、
  `ignore` の判定基準を `$CACHED_COMMIT_REF` からの差分に変更
- デプロイが成功し、ISS-053の文言修正5箇所すべてが公開サイトに反映されたことを確認

### 目的

コード変更が確実にデプロイされる状態に戻し、同じ取りこぼしが再発しないようにする。

### 所感

一番の教訓は、**Commit・Pushが成功していることと、公開されていることは別**という
当たり前の事実だった。今回はGitHub側だけを見て「完了」と判断していたため、
実機で見るまで気付けなかった。公開後に実サイトを確認する工程は、これまでも
やってきたが、今後は明確に手順の一部として位置づけたい。

もう一つは、**原因が2つ重なっていると切り分けが難しくなる**こと。原因1を
回避したら今度は原因2で落ちたため、症状が途中で入れ替わり、最初の見立て
（キャッシュ）→ 次の見立て（スキップ判定）→ 実際のエラー（ファイル名）と
段階的に絞り込む形になった。デプロイログを最後まで読むのが結局は近道だった。

なお、原因2の「リポジトリ全体が公開されていた」件は、`05_運営/アカウント一覧.md`
が公開URLで読める状態だったことを意味する。今回は中身がタイトルだけの空ファイル
（OneNoteからの移行時に階層だけ作り、センシティブな情報は移さなかった）だったため
実害はなかったが、Vaultをリポジトリ内に置く運用では、公開範囲の設定が
そのまま情報の露出範囲になるという点は意識しておきたい。
