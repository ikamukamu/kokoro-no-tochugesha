# 開発ルール

このページは「ココロの途中下車」開発における人向けのルール集です。 AI（Codex等）向けの簡潔なルールはリポジトリ直下の `AGENTS.md` を参照してください。 両者は矛盾しないよう、ルール変更時は両方を同時に更新します。

本ルールの目的は、「人とAIが同じ情報を参照しながら、安全かつ一貫性のある開発を 継続できる状態を維持すること」である。ルールは開発効率のためだけでなく、 設計意図や判断理由を将来へ引き継ぐための知識基盤として運用する。

## プロジェクトの基本方針

「ココロの途中下車」は、診断・治療ではなくセルフケアの補助を目的とした 静的シングルページWebアプリです。

- `index.html` にHTML/CSS/JavaScriptがほぼすべて内包された単一ファイル構成
- ビルドプロセス・package.json・テスト構成なし
- Netlifyで公開

## 情報の正本

|内容|正本の場所|
|---|---|
|設計・PBL・開発ログ・運営情報|`docs/`（Obsidian Vault、本リポジトリ内）|
|ソースコード|GitHub（main ブランチ）|
|Codexへの作業ルール|`AGENTS.md`|
|プロジェクト概要・技術構成|`README.md`|

Obsidianはエディタ、GitHubの`docs/`が正本。「どれが最新か」で迷ったら`docs/`を見る。

### docsの構成

```
docs/
├─00_ガイド
├─01_PBL
├─02_ISS
├─03_設計
├─04_開発ログ
└─05_運営
```

- `00_ガイド`：ルール・開発フロー・命名規則
- `01_PBL`：ISS一覧・バックログ運用ルール（次の停車駅）
- `02_ISS`：各ISSの詳細（要件・設計方針・実装メモ）
- `03_設計`：仕様・世界観・デザインガイド・システム構成
- `04_開発ログ`：開発履歴（月別）
- `05_運営`：VOC・リリース履歴・駅長だより・アカウント情報等

## AI利用ルール

- コード変更・Commit・Pushは、**明示的な指示があった場合のみ**AIに実行させる
- 調査・確認のみを依頼した場合、AIはコードを変更しない
- 勝手なリファクタリングは禁止。気になる点は提案として報告させ、実行判断は自分が行う
- 仕様や設計意図が不明な場合、AIに憶測させない。「たぶんこうだろう」という 善意の補完は許可しない。不明点は`docs/`を確認するか、自分に確認させる
- 実装途中で指示範囲を超える設計判断（データ構造・保存方式・画面遷移・主要UX変更） が必要になったら、AIはその場で進めず一度立ち止まって確認を取る （軽微な表示調整・バグ修正はこの限りではない）

### 設計意図を確認する順序

新規実装や仕様変更を行う場合は、AIに以下の順で確認させる。

```
01_PBL（何のためのタスクか）
    ↓
02_ISS（具体的な要件・設計方針）
    ↓
03_設計（全体の仕様・世界観との整合性）
    ↓
ソースコード（実装）
```

## GitHub運用

- ソースコードはGitHubを正本（正式な履歴）とする
- Codexは、GitHubリポジトリのローカルCloneを編集する （環境依存のため、具体的なパスはここに記載しない）
- `index.html`の動作確認後にCommitを行う
- 公開して問題ない状態になったらPushを行う
- Push後はNetlifyが自動デプロイを実行する

### 開発環境

- 作業フォルダはGitHubリポジトリを使用する
- CodexはGitHubリポジトリ内のファイルを編集する

### Commit / Pushルール

- Git操作前に `git status` で状態を確認し、意図しない変更が含まれていないか確認する
- Commit・Pushは自分の明示的な指示があった場合のみ
- Commit後は `docs/04_開発ログ/` に記録する

## バージョン管理

バージョンはSemantic Versioningを基本とする。

- Commitのバージョン番号は開発履歴として採番し `04_開発ログ` で管理する
- 利用者へ公開するバージョンは `05_運営/リリース履歴.md` で別途管理する

### 採番するかどうかの基準

- **採番する**：利用者が体感できる変更（新機能・UI刷新・音や見た目の変更など）
- **採番しない**：ドキュメントのみの変更・軽微な内部修正・Commit単位での 細かい調整

Commit単位で毎回採番する必要はない。「機能リリース」と呼べる単位でのみ バージョン番号を振る。

> **注記（2026-07-31）**：v1.0.4以降、ISS-002（マイコーピング機能）・ ISS-023（NR赤坂St ホーム画面リニューアル）は、本来なら採番すべき規模の 変更だったが、実際には番号が振られないまま公開されていたことが判明した。 過去のCommit履歴は書き換えず、v1.0.5（ISS-028, 030）から採番を再開する。 `04_開発ログ`・`05_運営/リリース履歴.md`にも同様の注記を残す。

例：

```
v1.0.0　初回公開
v1.0.1　バグ修正・小規模改善
v1.0.2　favicon追加
v1.0.3　Apple Touch Icon追加
（v1.0.4以降、ISS-002・ISS-023は未採番のまま公開）
v1.0.5　環境音の音質向上、星のまたたき再開（ISS-028, 030）
```

## 開発フロー

アイデア発生からPush・デプロイまでの詳細な流れは [[開発フロー]] を参照。 このページでは、開発ルールとして重要な原則のみ記載する。

「コード変更・Commit・Pushは、ユーザーの明示的な指示があった場合のみ行う」 という原則を最優先とし、フロー自体の詳細はこのページでは重複記載しない （フロー変更時の二重管理を避けるため）。

## ISS運用ルール

- ISSは `docs/02_ISS/ISS-XXX.md` に作成する
- 命名・記述形式は [[ISSテンプレート]] に従う
- 依存関係がある場合は「関連ISS」欄に明記する
- 状態管理は `docs/01_PBL/次の停車駅.md` のルールに従う

## 設計変更時のルール

- データ構造・保存方式・画面遷移・主要UXに関わる変更は、実装前に設計ノート （[[世界観]] / [[デザインガイド]] / [[システム構成]]）との整合性を確認する
- Firestore連携は現在休眠中。有効化する場合は以下を必ず設計し直す：
    - Local Storageの既存データをFirestoreへ自動同期する処理
    - 同一IDでの競合解決ルールの見直し
    - Firestore書き込み・削除失敗時の利用者向け通知

## ドキュメント管理（Obsidian記述ルール）

OneNote時代のルールから、Obsidianの特性に合わせて更新しています。 **特にリンクに関するルールはOneNote時代と真逆です**（Obsidianはリンクが前提の ツールのため、積極的に使う方針に変更）。

- 見出しはH1〜H3を基本とするが、必要であればH4まで許容する
- 色装飾は最小限（強調は太字`**text**`を優先）
- **ページ内リンク・段落リンクは積極的に使用する**（`[[ノート名]]` / `[[ノート名#見出し]]`） → OneNote時代は「使用しない」ルールだったが、Obsidianではリンクによる ナレッジの接続がAI・人間双方にとって価値になるため方針転換
- 関連ノートへの導線は、本文中のインラインリンクに加えて、末尾に 「関連ノート」セクションでも明示する
- 図はできる限りテキスト（表・Mermaid）で表現し、画像は補助的に使う （画像のみに頼ると、AIが内容を読み取れないため）

## ノート構成

- `00_ガイド` は、Vault全体の構成を管理するハブとする
    - 各セクションへのリンク・役割を掲載する（旧`🌟ガイド`ページに相当）
    - サイトマップは別ページを作成せず、`00_ガイド`内の索引ノートが兼ねる

各フォルダの役割は以下の通り。

- `00_ガイド`：ルール・開発フロー・命名規則など、プロジェクトの土台となる情報
- `01_PBL`：ISS一覧・バックログ運用ルール（次の停車駅）。実データはExcelを併用
- `02_ISS`：個々のISSの要件・設計方針・実装メモ・レビュー内容
- `03_設計`：世界観・デザインガイド・システム構成など、全体設計に関わる情報
- `04_開発ログ`：日々の実装・修正・調査の記録（月別ノート）
- `05_運営`：VOC・リリース履歴・駅長だより・アカウント/契約情報など運営関連

## ページ冒頭のルール

- 各ノートの冒頭には、そのノートの役割を1文で記載する 例：「このノートは『マイコーピング機能のISS-031』です。」
- 索引ノート（`00_ガイド`内など）に同じノートへのリンクを置く場合は、 同一の説明文を使い回す
