# ISS-063 更新情報の複数行対応と折りたたみ表示

> このテンプレートは「最初から全部埋める」ことを目的としない。
> ISSの進行に合わせて少しずつ育てる運用とする。

## 概要

`index.html`の`APP_NEWS`の`body`を配列化し、箇条書きで複数行を表示できるように
する。あわせて注意書き専用の項目を追加する。

さらに、1件あたりの分量が増えることへの対処として、各お知らせを折りたたみ形式に
変更する。折りたたんだ状態では日付・カテゴリ・タイトルと本文の1行目のみを表示し、
残りは開いたときに読めるようにする。

## 背景

[[ISS-058]]で追加した`APP_NEWS`は、1件につき`title`と`body`の2項目のみで、
`body`は1本のテキストである。

2026-09-25、OneNote時代に書かれていた過去のお知らせ文が見つかったが、現在の
形式では表現しきれないことが判明した。v1.0.3のお知らせ文は以下の3段構成に
なっている。

```
🐧ペンギン駅長がホーム画面にやってきました。
・ホーム画面へ追加した際に駅長アイコンが表示されます。
（すでにホーム画面に保存されている方は、一度削除してから再度ホーム画面登録してください）
```

見出し・箇条書き・括弧書きの注意の3層で、いまの`body`に流し込むと1本の
長文に潰れる。

## 目的

- お知らせ文を、書かれたときの構成のまま表示できるようにする
- 利用者が操作を求められるお知らせ（再登録が必要、など）で、注意書きを
  本文から区別して目立たせる
- [[リリース履歴]]に記録したお知らせ文を、痩せさせずにアプリへ転記できる
  ようにする

## 要件

### データ構造

- `APP_NEWS`の`body`を文字列から配列へ変更し、各要素を箇条書きの1行として
  表示する
- 注意書き用の項目（`note`等）を追加し、本文とは区別した見た目で表示する
- 注意書きは任意項目とし、無い場合は何も表示しない
- 既存10件のデータを新形式へ移行する
- **`body`の1行目は、折りたたんだ状態で見える唯一の本文になる。** 要約用の
  項目は別に設けず、1行目に一番大事なことを書く運用とする

### 表示

- 各お知らせを折りたたみ形式にする
- ヘッダーは2段構成とする
  - 上段：日付とカテゴリタグ
  - 下段：タイトル
  - スマートフォン幅（375px）でタイトルが折り返すため、1行に詰め込まない
- 折りたたんだ状態では、ヘッダーに加えて`body`の1行目のみを表示する
- 開くと`body`の2行目以降と注意書きが表示される
- **`body`が1行のみで注意書きも無いお知らせは、開閉の対象にしない。**
  開閉アイコンも出さず、常に全文が見えている状態にする

### 初期状態

- 未確認のお知らせは開いた状態、確認済みのお知らせは閉じた状態で表示する
- 確認済みかどうかは、[[ISS-058]]で実装済みの`kokoro_seen_news_id`
  （Local Storage）を使い、**日付で比較して判定する**
  - `kokoro_seen_news_id`に保存されているIDのお知らせより後のものを未確認とみなす
  - 保存値が無い場合（初回利用）は全件を未確認として扱う
  - 既読IDを配列で持つ形へは変更しない。Local Storageのキーの持ち方は現状のまま
- 月別タブを切り替えた場合も同じ判定で開閉を決める

### 変更しないもの

- カテゴリタグ、月別タブ、NEWバッジ、確認状態のLocal Storage保存の仕組み
- 更新情報セクション自体は[[ISS-059]]の決定どおり常時表示とし、
  アコーディオンには入れない

## 設計方針

## 判断理由

[[ISS-062]]（駅の掲示板スタイル化）で表示を作り直す予定があるため、その前に
データ構造を確定させておくと手戻りが出ない。逆に見た目を先に作ると、
形式拡張のたびに作り直しになる。

データ構造の変更を伴い、単独でも「過去のお知らせを元の構成のまま載せられる」
という価値があるため、[[ISS-058]]の追加修正ではなく独立したISSとする。

折りたたみを同じISSに含めるのは、複数行対応の副作用（1件あたりの分量が増え、
モーダルが縦に伸びる）への対処そのものだからである。データ構造と表示が直結して
おり、分けると片方だけ公開された状態で縦に伸びる。

要約用の項目を別に設けない理由は、項目が増えるほど[[リリース履歴]]と
`APP_NEWS`の両方で書く内容が増え、書き忘れが起きやすくなるため。
「1行目に一番大事なことを書く」という運用で代替する。

初期状態を「未確認のものを開く」としたのは、[[ISS-058]]で既に確認状態を
Local Storageへ保存しており、新しい仕組みを足さずに実現できるため。
全件閉じると初見の利用者が何も読まずに閉じる可能性があり、最新1件固定だと
複数件を一度に公開したときに取りこぼす。

## 実装メモ

- 対象：`index.html`の`APP_NEWS`定義と`renderAppNews()`
- `renderAppNews()`は現在`body`を`textContent`で1つの`<p>`へ入れている。
  配列化に伴い`<ul>`＋`<li>`の生成へ変更する
- 現在のヘッダーは`meta`という1つの`div`に日付・カテゴリ・タイトルを
  `append`している。2段化ではここを上段・下段に分ける
- 未確認判定は`NEWS_SEEN_STORAGE_KEY`（`kokoro_seen_news_id`）を参照する。
  この値は「最新のお知らせを見たか」の1件分しか持たないため、保存されているIDの
  お知らせより後のものを未確認とみなす日付比較で判定する。保存値が無い場合は
  全件を未確認として扱う
- `APP_NEWS`は新しい順に並んでいるため、保存済みIDの配列上の位置より前にある
  要素が未確認、という形でも判定できる
- 開閉は[[ISS-059]]で追加した2つのアコーディオンと同じ作法に揃える
  （見出し全体をボタン、`aria-expanded`、開閉アイコン）

## 実装結果

- Commit：`87c68d5`
- 実装内容：`APP_NEWS`の`body`を配列化し、箇条書き表示と注意書き欄へ対応。
  日付・カテゴリ・タイトルを同じ`flex flex-wrap`へ入れて1行の流し込みに変更。
  本文2行目以降と注意書きを折りたたみ、未確認のお知らせのみ開いた状態で表示。
  既読判定を`APP_NEWS.find`によるID一致から`id.slice(0, 10)`の日付比較へ変更し、
  NEWバッジ側も同じ判定へ統一。`#app-news-list`に`max-h-[14rem]`＋
  `overflow-y-auto`＋既存の`custom-scrollbar`と下端フェードを追加。
  掲載対象外の2件を削除し、`2026-09-22-app-news`の本文3行目を削除
- 変更ファイル：`index.html`
- 動作確認：公開サイトをスマートフォン幅（375×812px）で確認。未確認状態では
  最新のお知らせが開き、既読状態では閉じること、開閉ボタンが`aria-expanded`を
  切り替えること、一覧がスクロールすること（535px／表示領域224px）、
  ご意見フォームと「閉じる」が1画面に収まること、横スクロールが発生しないこと、
  ブラウザーコンソールにエラーが出ないことを確認

## レビュー・フィードバック

v1実装を実機で確認し、2026-09-28に以下のフィードバックが挙がった。

1. **ヘッダーの2段化はやりすぎだった。** カテゴリとタイトルの間で必ず改行が
   入るため間延びして見える。カテゴリに続けて空白でタイトルを置き、長いときだけ
   折り返す形にしたい
2. **更新情報に載せるかどうかは、デプロイ内容によって選びたい。** 採番した
   すべてを載せるのではなく、メイン機能に関係しない変更は掲載しない。現在
   載っている中では「7つの機能の使い方を載せました」「ご案内の文章を
   見直しました」の2件が該当する
3. **更新情報が長くなるとご意見フォームまで到達しにくい。** ご意見フォームは
   モーダル最下部にあるため、更新情報が縦に伸びるほど埋もれる。更新情報の
   一覧部分にスクロールを設けたい

## 要件（v2追加）

### ヘッダーを1行の流し込みへ

- 日付・カテゴリ・タイトルを同じ行に流し込み、幅が足りないときだけ折り返す
- カテゴリとタイトルの間で必ず改行する2段構成はやめる
- v1で追加した`heading`のラッパーと`meta`の分離を見直し、タイトルを
  日付・カテゴリと同じ`flex flex-wrap`の中へ入れる

### 掲載の可否をリリース履歴側で判断する

- 採番したすべてのお知らせを`APP_NEWS`へ載せるわけではない
- 掲載するかどうかは[[リリース履歴]]の「お知らせ文」に**アプリ掲載**の項目を
  設けて管理する。判断基準は「利用者がメイン機能で体感する変更かどうか」
- 以下2件を`APP_NEWS`から削除する（[[リリース履歴]]には残す）
  - `2026-09-24-feature-guides`「7つの機能の使い方を載せました」
  - `2026-09-09-help-copy`「ご案内の文章を見直しました」

### 掲載中のお知らせの本文を1行削除

- `2026-09-22-app-news`「更新情報のお知らせを始めました」の本文3行目
  「ご案内を開きやすく、閉じやすくしました。使い方とスマホの手順は、見たいものだけ
  開けます。」を削除し、本文を2行にする
- ご案内の中の操作性の話であり、利用者にとって「見たいもの」ではないため
- [[リリース履歴]]側も同時に削除済み

### 一覧にスクロールを設ける

- `#app-news-list`に最大高さと縦スクロールを設定する
- 月別タブ（`#app-news-tabs`）と見出しはスクロール領域の外に置き、常に見える
  ようにする
- スクロールできることが分かる見た目にする（下端のフェードなど）
- 最大高さの初期値は14rem前後とし、実機で見てから調整する

### 既読判定を削除に耐える形へ

- 現在の実装は`APP_NEWS`から保存済みIDを`find`して日付を得ているため、
  **そのIDのお知らせを削除すると判定が壊れる**（全件が未確認扱いになり、
  NEWバッジも再表示される）
- IDは先頭10文字が日付（`2026-09-24-feature-guides`→`2026-09-24`）なので、
  `APP_NEWS`を引かずに`id.slice(0, 10)`同士の比較で判定する
- Local Storageのキー名と保存値の形式は変更しない（既存利用者の既読状態を
  保持するため）

## 懸念事項

- 既存10件を移行する際、1行のままのものを無理に箇条書きへ割らないこと
- v1.0.0〜v1.0.2のお知らせ文は記録が残っておらず、遡って載せることはできない
- 日付比較による未確認判定は、`kokoro_seen_news_id`が更新されるタイミング
  （ご案内モーダルを開いたとき）に依存する。モーダルを開いた瞬間に全件が
  既読扱いになるため、開いた直後は全件が開いた状態、次に開いたときは全件が
  閉じた状態になる。意図した挙動かは実機で確認する
- 掲載しないお知らせが増えると、[[リリース履歴]]と`APP_NEWS`の件数が
  ずれていく。どちらが正本かを見失わないよう、リリース履歴側に必ず
  「アプリ掲載：なし」と明記する
- スクロール領域を設けると、更新情報が何件あるか一目で分からなくなるが、
  件数の表示は不要と判断した（2026-09-28）。利用者が更新の件数を気にする
  場面がないため
- ご案内モーダル内で開閉するものが3種類（使い方のご案内／スマホ手順／各お知らせ）
  になる。入れ子ではなく並列だが、実際に触ってみないと煩わしさは判断できない。
  まず実装して確認する
- 既存10件はすべて`body`が1行で注意書きも無いため、移行直後は開閉対象が
  1件も無い状態になる。折りたたみの挙動は、複数行のお知らせを追加してから
  でないと確認できない

## 完了条件

- `body`が配列で複数行の箇条書きとして表示される
- 注意書きが本文と区別された見た目で表示される
- 注意書きが無いお知らせで余計な余白や空要素が出ない
- ヘッダーが2段で表示され、スマートフォン幅でタイトルが崩れない
- 折りたたんだ状態で`body`の1行目が見え、開くと残りと注意書きが読める
- `body`が1行で注意書きも無いお知らせに、開閉アイコンが出ない
- 未確認のお知らせが開いた状態、確認済みが閉じた状態で表示される
- 既存10件が新形式へ移行され、表示崩れがない
- ヘッダーが1行で流し込まれ、長いタイトルのときだけ折り返す
- 掲載対象外の2件が`APP_NEWS`から消えている
- 更新情報の一覧がスクロールし、ご意見フォームまで到達しやすくなっている
- お知らせを削除しても、既読判定とNEWバッジが壊れない
- PC・スマートフォンの両方で表示を確認できる
